3논문 하나를 넣으면 일어나는 일

사용자는 “inbox에 넣은 논문 반영해줘”라고만 말하면 됩니다. 나머지는 이 순서대로 진행됩니다.

1
논문을 inbox/에 넣고 요청“반영해줘”
2
등록 — sb add원본을 raw/에 복사하고, 중복인지 확인하고, 쪽마다 <!-- page 128 --> 표시가 붙은 텍스트를 만듭니다.
3
원문 전체 읽기초록만 보고 쓰지 않습니다. 깨진 표·그림은 “Parsing Notes”에 적습니다.
4
논문 페이지 작성목적·설계·데이터·결과·한계를 항목마다 쪽 번호와 함께, 핵심 주장은 Claim으로 정리합니다.
5
기존 위키와 비교해서 고치기관련 개념·이론·방법 페이지가 이미 있으면 읽고, 이 논문이 기존 지식을 강화/축소/확장/충돌/대체하는지 판정해 반영합니다. 없으면 새로 만듭니다.
6
Overview · 열린 질문 갱신분야 전체의 “현재 이해”를 다시 쓰고, 한계·향후 연구에서 열린 질문을 뽑습니다.
7
목록 갱신과 검사 — sb index, sb lint끊어진 링크, 출처 없는 문장, 쪽 번호 없는 Claim 등을 찾아냅니다. 오류가 0이 될 때까지 에이전트가 고칩니다.
8
완료 기록 — sb done어떤 페이지를 왜 고쳤는지 log.md에 남깁니다.
9
보고를 받고 Obsidian에서 확인새 핵심 개념, 충돌 판정처럼 중요한 변경은 “검토 대기”로 따로 알려줍니다.

논문 한 편이 보통 5~15개 페이지를 건드립니다. 여러 편은 한 편씩 끝까지 처리합니다.

4지식의 4층 — 섞이지 않게 나눠 둡니다

원본, 원문 사실, 여러 자료를 합친 설명, 새 아이디어는 폴더부터 다릅니다. 아이디어가 검증된 사실처럼 보이는 일을 막기 위해서입니다.

① 원본raw/ — PDF 그대로. 누구도 수정하지 않습니다. 옆의 structured/는 쪽 번호가 붙은 텍스트입니다.
② 자료별 사실wiki/papers/, wiki/sources/ — 한 자료당 한 페이지. 원문에 적힌 것만 씁니다.
③ 종합 지식wiki/concepts/, theories/, methods/, overviews/ … — 여러 자료를 합친 설명. 모든 문장에 출처, 한 편에서만 나온 일반화는 “(단일 연구)” 표시.
④ 아이디어ideas/ — 가설·연구질문 후보. 확정 지식이 아닙니다. 근거·해석·추측을 나눠 적습니다.
📁 볼트(Obsidian에서 여는 폴더) 전체 구조 보기
store/ ← Obsidian에서 이 폴더를 볼트로 엽니다 ├── index.md 전체 페이지 목록 (sb index가 자동 생성) ├── log.md 작업 기록 (추가만 가능) ├── raw/ 원본 (수정 금지) ├── structured/ 쪽 번호가 붙은 텍스트 ├── wiki/ │ ├── papers/ sources/ 자료별 페이지 │ ├── concepts/ theories/ methods/ datasets/ │ ├── technologies/ researchers/ organizations/ topics/ │ ├── overviews/ 분야별 현재 이해 │ ├── questions/ 열린 질문 │ └── synthesis/ 저장해 둔 질의 답변 └── ideas/ ├── emerging/ research-questions/ hypotheses/ └── method-transfer/ domain-transfer/ rejected/

5에이전트가 지키는 규칙 (AGENTS.md)

규칙서는 Kiro·Claude Code·Codex가 자동으로 읽습니다. 사용자와 함께 계속 고쳐 나가는 문서입니다.

📌 출처는 쪽 번호까지

모든 서술 뒤에 이런 표시가 붙습니다.

(최윤진 외, 2020, p.128)

쪽 번호는 structured/의 <!-- page N -->에서 읽고, 추측하지 않습니다. Obsidian에서 누르면 논문 페이지로 이동합니다.

🚫 지어내지 않기

  • 원문에 없는 수치·저자·연도는 쓰지 않음 → “원문에 없음”
  • 초록이나 제목만 보고 페이지를 만들지 않음
  • 질문에는 위키에 있는 내용으로만 답하고, 없으면 “이 위키에는 자료가 없습니다”
  • 뉴스·블로그만으로 “확립된 결과”를 만들지 않음

✍️ 지우지 않고 고치기

새 논문이 기존 설명을 바꾸면 옛 문장을 남긴 채 ~~취소선~~ (superseded: …)으로 표시하고, 충돌은 “Conflicting Findings”에 양쪽 근거를 함께 적습니다. 페이지마다 Change Log에 날짜·근거·효과를 한 줄 남깁니다.

🔎 중요한 건 사람이 확인

아래 경우 페이지에 review: pending을 달고 보고에서 따로 알립니다.

새 핵심 개념·이론충돌·대체 판정 기존 내용 1/3 이상 수정새 Research Gap유망한 아이디어

새 논문이 기존 지식에 주는 영향 — 6가지 판정

💪 strengthen기존 결과를 강화
🎯 narrow적용 범위를 좁힘
🌱 extend새 맥락으로 확장
⚡ contradict기존 결과와 충돌
🔄 replace새 근거로 대체
➖ unchanged실질적 변화 없음

에이전트에게 시킬 수 있는 4가지 일

작업이렇게 말하면하는 일
Ingest 반영“inbox 논문 반영해줘”위 3번의 흐름대로 읽고 위키를 고침
Query 질문“기대 불일치 이론 쓴 연구들의 공통 한계는?”index.md부터 읽고 링크를 따라가 출처와 함께 답함. 좋은 답은 synthesis/에 저장할지 물어봄
Lint 점검“위키 점검해줘”기계 검사 + 페이지 간 모순, 중복 페이지, 빠진 개념 찾기
Idea 아이디어“연결 가능한 아이디어 찾아줘”빠진 관계, 충돌, 방법·이론 이전 가능성 등을 찾아 ideas/에 기록. 내 연구 프로젝트와 관련된 것부터 보여줌

6자동 검사 — LLM의 실수를 코드가 잡습니다

LLM이 쓴 결과를 그냥 믿지 않습니다. sb lint가 기계적으로 확인할 수 있는 것은 모두 확인합니다.

수준무엇을 잡나
오류없는 페이지로 가는 링크 · frontmatter 누락/깨짐 · wiki/에 섞인 아이디어 · 근거 자료가 없는 아이디어 · 반영했다는데 논문 페이지가 없음
경고출처가 없는 문장 · 쪽 번호 없는 Claim · 어디에도 연결되지 않은 논문 페이지 · 아무도 링크하지 않는 페이지 · 텍스트를 못 뽑은 자료(스캔본)
안내사용자 검토 대기 · 아직 반영 안 된 자료 · 목록 갱신 필요
✅ 실제로 테스트할 때 sb lint가 에이전트(저)의 실수 3건 — YAML 오류 1건, 출처 없는 문장 2건 — 을 잡았고, 고친 뒤 오류·경고가 0이 되었습니다.

👀 논문 페이지의 Claim 부분은 이렇게 생겼습니다 
## Claims
- **C1** 국내 여행 불만족 후기 → 가장 큰 부정 토픽은 물가
  | effect: 가중치 0.293 | context: '불편함' 앱 후기 454건, 2018
  | method: JST | confidence: medium | p.128
- **C3** 대중교통 부족 → 택시 이용 → 바가지요금 경험
  | direction: + | method: 키워드 네트워크 분석
  | confidence: low (연구자 해석) | p.132

Claim은 형식이 고정되어 있어서, 나중에 Knowledge Graph(노드·관계)를 만드는 재료가 됩니다. 연구자의 해석에서 나온 주장은 confidence를 낮게 표시합니다.

현재 이 Wiki의 근거는 연구 1편뿐이므로 아래 내용은 모두 (단일 연구)입니다.
이 연구에서는 국내 여행 불만족의 가장 큰 축이 금전적 비용(물가, 바가지요금)이었고
(최윤진 외, 2020, p.128), 네 여행지 모두에서 나타났습니다 (… p.131).

+Zotero 연동과 검색

논문은 Zotero에서 관리하고, 이 위키는 Zotero를 읽기만 합니다.

📚 Zotero에서 가져오기

  1. Zotero 설정 → 고급 → “Allow other applications … to communicate with Zotero” 켜기
  2. sb zotero sync -c "컬렉션 이름"
  3. 에이전트에게 “대기 중인 논문 반영해줘”
  • 제목·저자·연도·학술지·DOI·citekey는 Zotero 값을 그대로 사용 → 에이전트가 추측할 일이 없음
  • PDF가 없으면 서지 정보만 등록, 나중에 PDF를 붙이고 다시 sync하면 이어짐
  • 여러 번 실행해도 중복되지 않음
  • 논문 페이지의 zotero:// 링크를 누르면 Zotero 항목이 열림

사람은 Obsidian 기본 검색이면 충분합니다. 더 필요하면 플러그인:

  • Omnisearch — 더 똑똑한 키워드 검색, PDF 안까지
  • Smart Connections — 로컬 임베딩으로 “비슷한 내용” 찾기

에이전트는 Obsidian 플러그인을 쓸 수 없어서 index.md → 링크 → sb search 순서로 찾습니다. 페이지가 수천 개가 되면 그때 의미 검색을 추가할 계획입니다.

9시작하기

① 설치

# Python 3.11 이상
git clone https://github.com/LEE1026icarus/research-second-brain.git
cd research-second-brain
python -m venv .venv && source .venv/bin/activate
pip install -e .
sb init

② 연결

  • Obsidian: store/ 폴더를 볼트로 열기
  • Kiro: .kiro/steering/가 규칙을 자동으로 불러옴
  • Claude Code: CLAUDE.md가 규칙을 불러옴
  • Codex 등: AGENTS.md를 바로 읽음

③ 사용

논문 PDF를 inbox/에 넣고 에이전트에게 “반영해줘”. 한쪽에 에이전트, 한쪽에 Obsidian을 띄워 두고 결과를 바로 보면 됩니다.

🔒 이 저장소는 public이라 inbox/, raw/, structured/, 생성된 위키 페이지는 git에 올라가지 않게 막아 두었습니다(저작권). 위키도 git으로 관리하고 싶으면 저장소를 private로 바꾸고 .gitignore의 해당 부분을 지우면 됩니다.

10현재 상태 — 되는 것과 아직 안 되는 것

✅ 지금 되는 것

  • 원본 보존, 중복 탐지, 쪽 번호가 붙은 텍스트 변환
  • 에이전트 규칙서 (페이지 형식, 반영·질문·점검·아이디어 절차)
  • index.md 자동 목록, log.md 작업 기록
  • sb lint 자동 검사, 키워드 검색, 검토 대기 목록
  • Obsidian 링크·백링크·그래프 뷰
  • Zotero 연동 — 서지 정보·PDF 가져오기 (sb zotero sync)
  • 검색 — 사용자는 Obsidian 검색, 에이전트는 sb search
  • 테스트 20개 통과

⏳ 아직 안 되는 것

  • 실제 PDF 변환은 아직 검증 안 함 (테스트 환경에 PDF가 없었음). 2단 편집·표는 깨질 수 있음
  • HWP·DOCX·PPTX 파서 (OpenDataLoader PDF, unhwp 등 후보 조사 완료)
  • Gmail·Scholar Alert 자동 수집, 실시간 폴더 감시
  • Claim으로 Knowledge Graph 자동 생성
  • 에이전트용 의미 검색 (페이지가 많아지면 추가)
  • Zotero 연동은 가짜 Zotero 서버로만 테스트함 — 실제 Zotero 앱과는 아직 확인 안 함
  • 에이전트를 실행해야 반영됨 (완전 자동 아님)
  • 결과 품질은 사용하는 LLM 모델에 따라 달라짐
